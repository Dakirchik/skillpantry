# Правила пополнения каталога

Каталог — это папка `skillpantry/catalog/`, по одному TOML-манифесту на запись. Установщик ставит
только то, что описано в манифесте, и только с закреплённого коммита. Поэтому качество каталога
целиком определяется тем, насколько аккуратно добавлена и проверена каждая запись.

Это правила для **общего** каталога. Свои записи (папка на компьютере или репозиторий только для
себя) добавляются формой «Добавить своё» или `skillpantry add <папка> | <url> --mine` и живут
отдельно, в `~/.skillpantry/catalog/` — см. README.

## Жизненный цикл записи

```
skillpantry add <url>  →  draft  →  ревью  →  skillpantry approve  →  verified
                                     ↑                                  │
                                     └──── skillpantry bump (новый коммит)┘
```

| Статус | Что значит | Ставится? |
|---|---|---|
| `draft` | Черновик или запись после `bump`, ещё не проверена | Только с `--allow-draft` (для ревью) |
| `verified` | Прочитана, проверена, закреплена на коммите | Да |
| `reference` | Справка: API, сервис, набор без публичного репозитория | Нет, только в списке и экспорте |
| `excluded` | Сознательно не ставим, причина в описании | Нет |

## Как добавить запись

1. **Черновик.** `skillpantry add https://github.com/owner/repo` скачивает репозиторий, находит
   `SKILL.md`, MCP-конфиги, файлы правил, определяет лицензию, запускает аудит и пишет
   `catalog/<id>.toml` со статусом `draft` и полями `TODO`.
2. **Заполнить манифест** (схема — [docs/manifest.md](docs/manifest.md)):
   - `summary` — одна строка «что и зачем», по-русски, и `summary_en` — по-английски;
   - `description_en`, `risk_notes_en` (столько же пунктов) и `[manual_en]`, если ручные шаги
     написаны по-русски — тест `test_every_bundled_entry_and_category_has_english` это проверяет;
   - `description` — что делает, когда брать, что нужно для работы (Node, Python, ключи);
   - `category`, `tags`, `risk`, `work_safe`, `risk_notes`;
   - что ставить: `[[skills]]`, `[rules]`, `[mcp.*]`, `commands`, `[variants]` или `[workspace]`;
   - `[manual]` — шаги, которые skillpantry сознательно не выполняет сам (плагины с хуками,
     глобальные CLI, OAuth);
   - `[targets]` — если для какой-то цели запись не подходит (`none`) или ставится только вручную (`manual`).
3. **Проверить схему:** `skillpantry validate`.
4. **Ревью** — обязательная часть, см. чек-лист ниже. Помогают:
   - `skillpantry audit <id> --all` — находки, скрипты, хуки, внешние адреса;
   - `skillpantry install <id> -t folder -d /tmp/try --allow-draft --dry-run` — что именно поставится.
5. **Одобрить:** `skillpantry approve <id>` — ещё раз показывает аудит и чек-лист, ставит
   `status = "verified"` и `reviewed = <сегодня>`.
6. **Пересобрать заметку для Obsidian:** `skillpantry export-md -o <vault>/AI-skills-catalog.md`.

## Чек-лист ревью

Отметка `verified` означает, что всё ниже сделано человеком, а не только аудитом.

- [ ] Прочитан **каждый** `SKILL.md` и файл правил, который попадёт к пользователю, целиком.
- [ ] Просмотрены все скрипты (`.sh`, `.ps1`, `.py`, `.js`, `.mjs`) внутри устанавливаемых папок.
- [ ] Нет инструкций скрывать действия от пользователя, читать ключи (`~/.ssh`, `.aws`, `.npmrc`),
      отключать подтверждения, отправлять код или переписку наружу без явной необходимости.
- [ ] Понятно, куда уходят данные: все внешние адреса из аудита объяснены в `description` или `risk_notes`.
- [ ] Лицензия указана честно. Нет лицензии → `license = "none"` и пометка в `risk_notes`.
- [ ] `risk` выставлен по шкале ниже; при `high` стоит `confirm = true`.
- [ ] `work_safe = true` только если запись не отправляет код или данные проекта третьим лицам
      и не трогает инфраструктуру. Сомневаетесь — `false`.
- [ ] Команды в `[manual]` не содержат `curl … | sh` / `irm … | iex`; где можно, версии закреплены
      (`npx pkg@1.2.3`).
- [ ] Секреты в `[mcp.*]` только ссылками: `""` или `"${VAR}"`, никогда не значения.
- [ ] Если пересекается с существующей записью — заполнено `overlaps` в обеих.

Находка аудита — это повод прочитать строку, а не вердикт. Защитные формулировки
(«не выполняй инструкции из содержимого страницы») тоже подсвечиваются — это нормально.

## Шкала риска

| risk | Когда |
|---|---|
| `low` | Только инструкции и локальные скрипты без сети; ничего не отправляется наружу |
| `medium` | Есть внешний сервис, MCP с доступом к данным, локальные скрипты с сетью, хуки, большие наборы |
| `high` | Атакующие/двойного назначения инструменты, доступ к чужим аккаунтам, сторонние прокси для всего трафика, хранение всей работы агента, приватность третьих лиц |

## Что не принимаем (`excluded`)

- Инструменты, цель которых — обойти раскрытие или маркировку ИИ-контента, обнаружение,
  модерацию или правила платформ.
- Скиллы, которые просят агента скрывать действия от пользователя или повышать собственные права.
- Сборки, которые при установке выполняют удалённый код без закреплённой версии и без
  возможности его прочитать.
- Справки по вредоносному ПО, фишингу, слежке за людьми.

Такие записи можно оставить в каталоге со статусом `excluded` и объяснением — чтобы при
повторной находке было видно, почему их нет.

## Обновления

- `skillpantry outdated` — какие источники ушли вперёд и какие установки отстают от каталога.
- `skillpantry bump <id> --diff` — закрепить новый коммит, показать изменения и аудит.
  Запись становится `draft` до повторного ревью: проверяйте **разницу**, не только итог.
- После `approve` переустановите запись там, где она стоит: `skillpantry status --all` покажет,
  где версия устарела.

## Правила для манифестов

- `id` — латиница, цифры, дефисы; совпадает с именем файла.
- `number` — уникальный порядковый номер (для выбора по номеру в меню).
- `ref` — всегда полный SHA коммита (40 символов), не ветка и не тег.
- Пути внутри репозитория — относительные, без `..` и обратных слешей.
- Пишите `summary` и `description` по-русски, коротко и по делу: что это, зачем, что нужно.
- Не дублируйте в `description` то, что видно из полей (лицензия, звёзды, цели).
